# rag-flow — 이슈부터 PR까지 표준 절차

AGENTS.md의 작업 흐름을 실행 가능한 단계로 편 것이다. **단계를 건너뛰지 마라** —
"간단해 보인다"·"이미 알고 있다"는 생략 사유가 아니다(이 저장소에서 설계 초안의 사실 오류가
여러 번 나왔다). 경량 우회는 사용자가 명시적으로 승인한 경우에만. 이전 세션에서 이미 했던
단계도 **크로스체크로 다시 한다** — 같으면 확인한 것이고, 다르면 잡아낸 것이다.

인자: 작업 설명(필수). `#N`이 있으면 그 이슈로, `branch=…`가 있으면 그 브랜치로. 없으면 아래대로 찾거나 만든다.

## 1. 이슈 확인/생성

1. `#N`이 있으면 그 이슈를 읽는다. 본문이 분석 결과와 다르면 **이슈를 먼저 최신화**한다 — 낡은 이슈를 근거로 설계하지 마라.
2. 없으면 키워드 2~3개로 `gh issue list --search "…" --state all`을 검색한다. **비슷한 게 있으면 후보를 보여주고 그것인지 묻는다** — 임의로 고르지 마라.
3. 없으면 만든다. 본문 틀:
   - `## 배경` — 왜 지금 하는가, 무엇이 문제인가. **실측 수치**(어느 커밋·어느 축인지 함께)와 선행 이슈
   - `## 범위` — 할 것과 **하지 않을 것**(기각·보류한 안도 한 줄씩, 이유와 함께)
   - `## 완료 기준` — 체크박스. 측정으로 닫히는 항목은 목표치를 적는다
   - `## 관련` — 이슈·PR 번호
4. 이슈 번호를 이후 모든 산출물(브랜치 슬러그·커밋·PR)에 연결한다.

## 2. 워크트리 브랜치

`git fetch --prune origin` 먼저. 같은 슬러그의 브랜치가 로컬·원격에 **있으면 그대로 쓴다** — 새로 만들지 마라.
같은 주제의 열린 PR 브랜치가 있어 그 위에 쌓아야 할지 애매하면 묻는다(스택이면 토대 PR이 먼저 머지되도록 순서를 잡는다).

```bash
git worktree add -b <type>/issue-<N>-<slug> ../consult-agent-issue<N> origin/main
cp .env ../consult-agent-issue<N>/.env   # 필수 — .env는 gitignore라 워크트리에 안 딸려온다
```

- `.env` 복사를 빠뜨리면 개발계 DB 인증 실패(#122에서 실측). `.env.dev`의 비번은 플레이스홀더다.
  측정이 필요한 작업이면 `eval/gold_private`·`eval/results`도 챙긴다(둘 다 gitignore).
- 이후 모든 파일 작업은 워크트리 안에서만. 원본 저장소 경로의 파일은 절대 건드리지 마라.

## 3. 피처데브 (생략 금지)

`feature-dev` 스킬(플러그인)을 호출해 전 단계를 밟는다: **탐색 → 질문 → 설계 → 구현 → 리뷰**.
들어가기 전에 AGENTS.md를 다시 읽는다 — 계층 규칙(leaf→조립점→진입점, 역방향 import 금지)과
"이름이 비슷해서 헷갈리는 것" 목록이 설계 오류의 단골 원인이다.

- 탐색: code-explorer 에이전트 병렬 투입 + 반환된 핵심 파일을 직접 읽는다. 정의점은 `grep -rn "정의점"`으로 찾는다.
- 질문: 모호한 결정은 추측하지 말고 묻는다. **답이 뻔해 보여도 낸다** — 권장안을 붙여 "권장대로 갈까요"로 물으면 사용자 비용은 한 마디다.
- 설계: 표(대안 × 기준)로 비교하고 **추천 1개와 이유**를 쓴다. **구현은 사용자 승인 후에만.**
- **결정은 축 하나씩.** 질문·설계·리뷰 지적은 전부 결정이다. 여럿이면 한 메시지에 다 묻지 않는다.
  축 하나마다 ① 코드·문서에서 확인한 사실 ② 대안 표(안 × 내용 × 대가) ③ 추천 1개와 이유를 적고
  "a로 갈까?"로 묻는다. 사용자가 고르면 "결정 N = a"로 확정하고 다음 축으로. 앞 축의 선택이 뒤 축의
  대안을 바꾸면 반영해서 낸다. 순서는 영향이 큰 것(경계·범위)부터, 문서 정리 같은 작은 것은 뒤로.
- 설계에서 "반드시/절대" 문장이 나오면 정의점 docstring(또는 AGENTS.md)에 적고, 그 항목을 **강제하는 테스트**를 구현과 같이 짠다.
  강제 수단 칸을 비워 두지 않는다 — AGENTS.md의 경로·심볼·숫자는 `tests/test_docs_freshness.py`가 그 예다.
- 구현 중 새 결정이 필요하면 멈추고 묻는다. 추측으로 채우지 않는다.
- 리뷰: code-reviewer 에이전트 결과는 **수정하지 말고 먼저 보고**한다 — 전체 목록(심각도·파일:행·한 줄)을 보인 뒤
  **지적 하나씩** 위 형식으로 묻고 사용자가 정한다. 리뷰어 주장은 직접 확인한 뒤 옮긴다(틀린 지적도 온다).
- 요약에는 **무엇을 만들었나 / 핵심 결정 / 변경 파일 / 남은 것**을 쓴다.

측정 규율(AGENTS.md): 프롬프트·설정·파서를 바꿔 측정할 때는 바뀐 결과물을 **값으로 검증한 뒤**
측정한다(조립이 틀린 채로 측정한 사고가 있었다). 수치만 보고하지 말고 실제 생성물을 파일로 떨궈
사람이 읽을 수 있게 한다. 오답의 원인 축이 애매하면 `answer-triage` 스킬로 가른 뒤 설계한다.

전체 테스트(`pytest`, DB·Redis·OpenSearch 필요)를 돌려 실패가 있으면 전부 명시한다.

**품질 게이트(CI 대신 여기서 강제한다, #302)** — 구현과 리뷰 사이에 돌린다. 판단 기준은 AGENTS.md "코드 품질 기준".
- 새로 만든 파일과 크게 고친 파일은 `ruff format <파일>`·`ruff check --fix <파일>`로 맞춘다(기존 파일 일괄 포맷은 #303 — 이 PR에서 하지 마라).
- `pytest tests/test_code_quality.py`가 통과해야 리뷰로 넘어간다. 실패 = 새 위반·악화다. **고쳐서 통과시킨다** —
  복잡도·분기·인자·크기 초과는 "책임을 나누라"는 신호다. 고칠 수 없는 증가(파일·함수 이름 변경 포함)만
  `QUALITY_BASELINE_UPDATE=1 QUALITY_ALLOW_GROWTH=1`로 기준선에 올리고, **사용자에게 사유를 보고**한 뒤 PR 본문 `## 테스트`에 적는다.
- 경고("품질 개선 N건")가 나오면 `QUALITY_BASELINE_UPDATE=1 pytest tests/test_code_quality.py`로 기준선을 조여 같은 PR에 넣는다.
- 리뷰어 프롬프트에 3·4·5번(데이터는 dict 대신 dataclass/TypedDict, 클래스 절제, 공개 함수 타입 힌트)을 점검 항목으로 넣는다 — 기계 검사가 없는 규칙이다.
- ruff가 없다는 skip이 나오면 `pip install -r requirements-dev.txt` 후 다시 돌린다 — skip을 통과로 보고하지 마라.

## 4. E2E 테스트케이스 리스트업

자동 테스트가 통과했다고 끝이 아니다. 사람이 실제로 눌러봐야 하는 케이스를 체크박스로 만든다.

- 절로 나눈다 — 보통 `기능 동작` / `회귀` / `운영 확인(로그·지표·색인 상태)`
- 각 항목은 "무엇을 하면 → 무엇이 보여야 한다" 한 줄. 선행 조건(설정 토글·재인제스트 필요 등)은 절 맨 위에 인용문으로
- 단위 테스트가 이미 덮는 부분은 "(테스트 X로 검증됨, E2E는 재확인만)"을 달아 중복 작업을 막는다
- 환경이 필요해 지금 못 하는 항목(GPU·부하·외부 장애)은 그 이유를 적는다
- 이전 PR의 E2E 목록에서 **이번 변경으로 전제가 바뀐 항목**이 있으면 짚는다
- 목록은 5절에서 갱신한 뒤 PR 본문에 포함한다

## 5. E2E 항목의 테스트 전환 (PR 전, 생략 금지)

4절 목록을 항목마다 다시 보고 **테스트 코드로 옮길 수 있는지** 판정한 뒤, 옮길 수 있는 것은 짜서 **실제로 돌린다**.
"사람이 눌러봐야 한다"고 적은 것 중 상당수는 실제로 테스트가 된다 — 판정은 **단위 먼저, 안 되면 통합** 순서로 한다.

- **단위**: 순수 함수·검증 로직·스키마 제약처럼 DB·네트워크 없이 직접 호출할 수 있는 것. 수 초면 돌고
  회귀를 가장 싸게 잡으므로 **여기서 덮을 수 있는 것을 통합으로 올리지 마라**
- **통합**: HTTP 왕복·DB 상태 전이·색인 반영처럼 실제 인프라를 거쳐야 의미가 생기는 것
- 판정은 표로: `E2E 항목 | 테스트로(단위/통합) | 방법`. 옮기는 항목이 없다고 결론 나면 그 이유를 적는다
- 통합 테스트는 필요한 인프라를 **실제로 띄워서 돌린다.** 환경 부재로 스킵된 채 "단위 통과"만 보고 PR로 가지 마라 — 단위로는 절대 안 잡히는 기동·연결 버그가 여기서 나온다
- 남기는 항목은 이유가 있어야 한다: 외부 장애 주입, 실제 모델 응답 품질, 부하, UI 육안 확인처럼 프로세스 안에서 재현 안 되는 것
- 전환 뒤 4절 목록을 갱신한다 — 옮긴 항목은 "(테스트 X로 검증됨, 재확인만)", 나머지만 수동 항목으로 남긴다

## 6. PR 작성

1. **커밋은 사용자가 시킬 때 한다.** 커밋 전 `git status`로 남의 변경이 섞이지 않았는지 확인(여러 세션이 같은 트리를 쓸 수 있다).
   **스테이징은 이번 변경 파일만 경로로 지정한다** — 이 트리에는 초안·공유 문서·미추적 디렉터리가 상시 굴러다니므로 `git add -A`는 쓰지 않는다.
2. 커밋 메시지는 `<type>(#N): 한국어 한 줄` + 본문 불릿(판단 근거·실측치), 끝에 세션 지침의 Co-Authored-By 줄.
3. `git push -u origin <branch>` 후 `gh pr create`. 본문 틀:
   - 첫 줄 `Closes #N` — 기본 브랜치가 `main`이라 머지 시 자동 종료된다. 일부만 끝내는 PR이면 `Refs #N`
   - `## 요약` — 무엇이 어떻게 달라지나, 가능하면 **실제 출력 샘플**(바뀐 청크·답변·지표 전후)
   - `## 변경 내용` — 절별로. 공개 API 삭제·시그니처 변경·설정 기본값 변경·재인제스트 필요는 ⚠️로 따로
   - `## 테스트` — 돌린 명령과 결과, 신규/수정 테스트. 품질 게이트 결과(기준선을 조였으면 줄어든 수, 늘렸으면 사유)
   - `## 리뷰 반영` — 3절 리뷰에서 고친 것 / 보류한 것과 이유
   - `## E2E 테스트 리스트` — 5절에서 갱신한 4절 목록(테스트로 옮긴 것과 수동으로 남긴 것 구분)
   - `## 문서` — AGENTS.md·docstring 정의점·메모리 중 이 PR로 바뀐 것. AGENTS.md를 고쳤으면 `tests/test_docs_freshness.py`를 돌린 결과
   - `## 후속` — 별도 PR로 미룬 것(이슈 번호)
   - 끝에 세션 지침의 Generated with 줄
4. **머지는 사용자 지시로만.** PR 생성까지가 이 절차의 끝이다.
   머지 후(사용자 지시 시): `git fetch --prune`, 원격·로컬 브랜치 정리, 원본 트리에서 `git worktree remove ../consult-agent-issue<N>` — 남겨 두지 않는다.

## 7. 이슈 갱신

- PR 생성 직후 이슈에 코멘트: PR 링크 + 이 PR이 이슈 범위 중 어디까지인지.
- 머지 후 범위가 끝났으면 결과(실측치 전후)를 코멘트로 남긴다. `Closes`로 자동 종료되지 않은 이슈는 직접 닫는다.
  일부만 끝났으면 남은 범위를 코멘트로 적고, 미룬 것은 새 이슈 번호를 받아 연결한다.

## 하지 말 것

AGENTS.md의 절대 규칙 전부, 더해서: 단계 건너뛰기("이미 알고 있다"는 이유가 아니다) · force push ·
`git add -A` · 사용자 승인 전 구현 · 환경 없이 스킵된 통합 테스트를 "통과"로 보고 ·
품질 게이트 실패를 기준선 증가로 덮기(사유 보고 없이).
