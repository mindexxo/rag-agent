# rag-flow — 이슈부터 PR까지 표준 절차

AGENTS.md의 작업 흐름을 실행 가능한 단계로 편 것이다. **단계를 건너뛰지 마라** —
"간단해 보인다"는 생략 사유가 아니다(이 저장소에서 설계 초안의 사실 오류가 여러 번 나왔다).
경량 우회는 사용자가 명시적으로 승인한 경우에만.

## 1. 이슈 생성

- `gh issue create` — **무엇을 왜** 하는지 적고 시작한다. 배경(근거 실측치·선행 이슈), 스콥,
  완료 기준을 본문에 명시.
- 이미 이슈가 있으면 생성 대신 본문 검증: 분석 결과가 이슈 본문과 다르면 **이슈를 먼저
  최신화**한다 — 낡은 이슈를 근거로 설계하지 마라.

## 2. 워크트리 브랜치

```bash
git worktree add -b <type>/issue-<N>-<slug> ../consult-agent-issue<N> origin/main
cp .env ../consult-agent-issue<N>/.env   # 필수 — .env는 gitignore라 워크트리에 안 딸려온다
```

- `.env` 복사를 빠뜨리면 개발계 DB 인증 실패(#122에서 실측). `.env.dev`의 비번은 플레이스홀더다.
- 이후 모든 파일 작업은 워크트리 안에서만. 원본 저장소 경로의 파일은 절대 건드리지 마라.

## 3. 피처데브 (생략 금지)

`feature-dev` 스킬(플러그인)을 호출해 전 단계를 밟는다: **탐색 → 질문 → 설계 → 구현 → 리뷰**.

- 탐색: code-explorer 에이전트 병렬 투입 + 반환된 핵심 파일을 직접 읽는다.
- 질문: 모호한 결정은 추측하지 말고 사용자에게 묻는다(설계 전에).
- 설계: 복수 안 비교 + 추천. **구현은 사용자 승인 후에만.**
- 리뷰: code-reviewer 에이전트로 버그·규약·단순성 검토.

측정 규율(AGENTS.md): 프롬프트·설정을 바꿔 측정할 때는 바뀐 결과물을 **값으로 검증한 뒤**
측정한다. 수치만 보고하지 말고 실제 생성물을 파일로 떨궈 사람이 읽을 수 있게 한다.

## 4. E2E 테스트케이스 리스트업

자동 테스트가 통과했다고 끝이 아니다. 사람이 실제로 눌러봐야 하는 케이스를 목록으로 만든다.

- 테스트 코드로 덮을 수 있는 케이스가 섞여 있으면 **먼저 테스트로 옮기고**, 남는 것만
  수동 목록에 남긴다.
- 목록은 다음 단계의 PR 본문에 포함한다.

## 5. PR 작성

- 커밋 전 `git status`로 남의 변경이 섞이지 않았는지 확인(여러 세션이 같은 트리를 쓸 수 있다).
- 커밋 메시지·PR 본문은 한국어, 판단 근거와 실측치 포함. E2E 수동 목록을 PR 본문에 싣는다.
- **머지는 사용자 지시로만.** PR 생성까지가 이 절차의 끝이다.
- 머지 후(사용자 지시 시): 원격 브랜치 정리, 이슈 코멘트/클로즈, 워크트리 제거.
