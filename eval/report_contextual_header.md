# 청크 머리말과 잘린 맥락 — Contextual Retrieval 비교 (#234)

측정 커밋 main `b58407d`, 개발계 색인 `kms_chunks_v1` 스냅숏(2026-10-20, 1,929조각 — 측정 테넌트 1,222조각만 조건별로 바꿈).
도구 `python -m eval.contextual_header`(정의점 docstring). 조건마다 임시 인덱스를 만들어 운영 검색(`retrieve_candidates`)을 그대로
돌렸다. 검색은 조건마다 2회 — 리랭커(TEI) 흔들림으로 ±0.001 안에서만 달라 표는 1회차 값이다. 답변은 2회 평균이다.
운영 코드·설정 변경 없음. 측정 중 공유 색인이 바뀌지 않았음을 확인했다(측정 조각 1,222개 그대로, 새 조각 0).

## 결론

**지금은 도입하지 않는다. 서비스 오픈 후 필요하면 Contextual Retrieval(CR) 도입을 검토한다.**

- 현행 머리말('파일명 > 헤딩')은 전체적으로 일한다. 하지만 **청크 경계에서 잘린 맥락은 거의 메우지 못한다**.
- CR과 규칙 맥락 줄은 맥락이 잘린 질문의 검색 순위를 크게 올린다.
- 그러나 지금 코퍼스 규모에서는 정답 조각이 거의 언제나 상위 5 근거 안에 들어와(맥락 셋 R@5 0.947~1.0) **답변 품질은 나아지지 않았다**.
- 순위 차이가 답으로 이어지는 것은 문서가 늘어 정답 조각이 상위 5 밖으로 밀릴 때다(#235).

## 조건

| 조건 | 검색용 텍스트(임베딩·BM25 어휘 필드·리랭커 입력) |
|---|---|
| none | 본문만 |
| **header** | 현행 — `파일명 > 헤딩` + 본문 |
| cr | LLM(사내 vLLM 14B, 사고 모드 끔, 온도 0)이 문서와 조각을 보고 쓴 맥락 문장 + 현행 머리말 + 본문 |
| rule | 현행 머리말 + 잘린 맥락 줄(목록 소제목·목록 머리, '단,'·'이 경우'는 앞 조각 마지막 줄) + 본문 — 20조각만 해당 |

모델이 받는 근거 본문은 모든 조건에서 원문이다(운영과 같다).

## 맥락 셋 — 정답 조각의 맥락이 잘린 질문 38문항

| 출처 | 문항 | 잘린 모양 |
|---|---|---|
| 모의 상담스크립트 TXT (`*_cx1NN`) | 10 | `[상황 N] …` 소제목 아래 단계가 다음 조각으로 넘어감. TXT라 헤딩 없음 |
| 합성 분기 보고서 (`aromanica_cx00N`, `aromanica_2[01]_*`) | 8 | 주체·시점이 첫 문단에만. 1분기·2분기 보고서가 같은 모양이라 맥락 없이는 구별 불가 |
| 실문서 (gold_private) | 7 | '단,' 문장·목록 머리가 앞 조각에, 또는 조 제목이 헤딩에 있는 대조군 |
| #245 합성 (`*_cb0NN`) | 13 | 목록 머리·표 설명·'이 경우' |

후보는 `eval/chunk_boundary.py` 진단과 "앞을 가리키는 말로 시작하는 조각" 전수 스캔에서 골랐다.
오버랩으로 사실 문장이 소제목 조각에도 실린 2문항은 맥락 의존이 아니어서 뺐다.

## 결과

### 검색 — 정답 조각 1위 비율(Hit@1)

| | none | **header** | cr | rule |
|---|---|---|---|---|
| 전체 골드 712 | 0.764 | **0.817** | 0.834 | 0.834 |
| **맥락 셋 38** | 0.526 | **0.579** | **0.895** | 0.816 |
| └ 모의 상담스크립트 10 | 0.30 | 0.20 | 0.70 | 0.90 |
| └ 분기 보고서 8 | 0.12 | 0.25 | 0.88 | 0.25 |
| └ 실문서 7 | 0.71 | 0.86 | 1.00 | 1.00 |
| └ #245 합성 13 | 0.85 | 0.92 | 1.00 | 1.00 |

- 머리말을 빼면 맥락 셋 밖 674문항에서 51문항이 나빠지고 15문항이 좋아진다 — 머리말은 일한다(8/3 도입 효과의 재확인).
- TXT 스크립트는 머리말이 파일명뿐이라 머리말이 오히려 순위를 낮췄다(0.30 → 0.20).

### 부작용 — 맥락 셋 밖 674문항, header 대비

| | cr | rule |
|---|---|---|
| 좋아짐 | 23 | 3 |
| 나빠짐 | **23** | **0** |

CR은 평균을 바꾸지 않고 순위만 흔든다. rule은 20조각만 건드려 부작용이 없다.

### 답변 — 맥락 셋 EPCov(규칙+Claude 심판, 2회 평균)

| | none | header | cr | rule |
|---|---|---|---|---|
| 1회 | 0.882 | 0.829 | 0.816 | 0.842 |
| 2회 | 0.855 | 0.803 | 0.855 | 0.803 |
| 평균 | 0.868 | 0.816 | 0.836 | 0.822 |

cr·rule은 header보다 낫다고 할 수 없다(회차마다 순서가 바뀐다). none이 header보다 두 회차 모두 약 0.05 높았는데, 38문항에서 1~2문항
차이라 원인을 따로 확인하지 않았다 — 검색 순위가 오른 조건(cr·rule)에서도 답이 좋아지지 않았다는 것이 이 측정의 결론이다.
분기 보고서 예(aromanica_cx001, header): 1위 근거는 1분기 조각이었지만 상위 5에 2분기 조각이 함께 있어 모델이 "2분기 4,120건"으로 맞게
답했다. EPCov가 0.5인 것은 증감률(18%)을 빼고 답해서다.

## 해석과 한계

- **rule의 성적은 깎아서 읽는다.** 맥락 셋의 상당수가 rule과 같은 진단 규칙(`eval/chunk_boundary`)으로 찾은 조각에서 나왔다.
  규칙이 모르는 모양(분기 보고서)에서는 header와 같았다(0.25). CR은 문항 출처와 무관하게 읽는다.
- CR 비용(실측, 결과 파일 생성·수정 시각 기준): 1,222조각 생성 약 6분(동시 8). 운영이라면 문서마다 조각 수만큼 LLM 호출과 문서 전체 입력(최대 약 2만 토큰 × 조각 수)이
  든다. 이 호출은 상담 응답과 같은 vLLM을 쓴다. 문서를 고칠 때마다 다시 생성해야 하고, LLM 실패를 어떻게 처리할지(#223 캡션과 같은 문제)도 정해야 한다.
- 맥락 셋은 38문항이라 그룹별 수치는 1문항이 0.1~0.13씩 움직인다.

## 후속

- 서비스 오픈 후 실사용 로그에서 "맥락이 잘려 못 찾는" 사례가 보이거나 문서 규모가 커지면(#235) CR 도입을 검토한다. 이 도구로 다시 잰다
  — `contexts → build → measure → drop`.
- #266(목록 맥락 보존) 보류 사유를 바로잡는다: "헤딩 경로로 커버된다"는 틀렸다(맥락 셋 0.579). 실제 사유는 "검색 순위는 오르지만
  지금 규모에선 답에 영향이 없다".
