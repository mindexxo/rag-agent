- 측정: 2026-09-12, 브랜치 `feat/issue-139-opensearch` @ `c65a40f`(main #137·#143 머지 후) 기준
- 실행: 7테넌트 99문서 `eval.reindex_documents --tenant`(pg 백엔드, docling) → `eval._os_index --recreate`
  (PG→측정 인덱스 `kms_chunks_eval` 복사) → `eval._hybrid_ablation --os`
- 대상: gold v2+hard95 450문항(멀티턴 제외 TYPES 10종), **skip 0** — 재청킹에도 `resolve_gold`가 전부 풀렸다
- 코퍼스: 골드 6테넌트 **604청크**(v1 504 → docling이 PDF를 더 잘게·충실하게 자름) + inticube 363 + 기타 = 측정 인덱스 1073
- 엔진: OpenSearch 2.18.0 로컬 컨테이너 — **성능 축은 여전히 재지 않았다**(v1과 같은 사유)

**v1(`report_os_ablation_v1.md`)과 수치를 직접 비교하지 마라.** 청킹과 임베딩이 둘 다 다시 계산돼
눈금이 새로 잡혔다. 유효한 비교는 **같은 실행 안의 PG vs OS**뿐이다 — 그게 이 어블레이션의 목적이다.

## 결론 — v1과 같다

1. **배선 게이트 5개 통과.** kNN 동형성 후보 겹침 **1.000**·top1 **1.000**(450문항). 벡터는 PG에서
   바이트 단위로 복사했으므로(TEI 호출 비결정성 1.4e-4를 배제) 이 1.000은 "매핑·필터·거리 환산에
   어긋난 곳이 없다"는 뜻이다. v1 단서 그대로: 1073청크는 `approximate_threshold`(15000) 미만이라
   OpenSearch는 정확 탐색 — "HNSW ≡ HNSW"의 근거는 아니다.
2. **엔진 교체의 이득은 0.** 7 variant의 차이가 다시 문항 하나다. 어휘 채널 주입 상방은 4채널 전부
   0/450 — 청킹을 바꿨어도 "dense가 놓친 정답을 어휘가 구제하는" 자리가 생기지 않았다.

## 읽는 법 — v1과 같은 분해

- `os_knn` vs `baseline` → 벡터 검색 차이 **없음**(겹침 1.000).
- `hyb_os_bigram` vs `hyb_bigram` → BM25 구현 차이 **없음** — 토큰이 같으면 Lucene과 앱 계산이 같은 순위를 낸다(v1 재확인).
- `hyb_os_nori` vs `hyb_os_bigram` → 토크나이저 차이 **잡음** — Nori 단독 리콜이 bigram과 같은 436이고 최종은 1문항 낮다.
- `os_hybrid` vs `os_knn` → 엔진 융합의 상방 **없음** — 주입 상방 0 조건에서 융합 방식은 결과를 못 바꾼다.

### 형태소 계열이 놓친 한 문항

`harim_pp003`(paraphrase, "그냥 마음이 바뀌어서요. 산 닭 돌려보내고 싶은데 되나요?") — **v1과 정확히 같은
문항**이다. 청킹·임베딩이 바뀌었는데도 kiwi·Nori 두 형태소 채널만 이 문항을 놓친다: 형태소 토크나이저가
구어체 패러프레이즈를 깎는 패턴이 청킹과 무관한 성질임을 두 눈금에서 확인한 셈이다.
v1에서 함께 놓쳤던 `os_hybrid`는 v2에선 baseline과 같다(0.820) — 융합 가중 0.7/0.3에서 dense가 이겼다.

## 청킹 변경의 부수 관측 (이 A/B의 결론이 아님)

같은 골드·같은 채점에서 PG baseline이 v1 Hit@1 0.811 → **0.820**, hard Hit@1 0.633 → **0.700**으로
올랐다. 이건 엔진이 아니라 **#137·#143(docling 청킹)의 효과**다 — 특히 고난도 구간 +6.7pp. 이 리포트의
소관은 아니지만 같은 눈금으로 잡힌 값이라 기록한다. 임베딩 재계산의 잡음도 섞여 있으니 단정은 #137 쪽에서.
