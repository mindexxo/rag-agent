# #235 문서 규모가 커질 때 검색 품질 — 노이즈 주입 곡선·근사 탐색 일치율·IDF 공유 영향

측정: 커밋 7696216 기준 하네스(`eval/scale_noise`), 운영 인덱스 `kms_chunks_v1` 복사본, 측정 테넌트 inticube 골드 141문항
(single_fact·paraphrase·rare_lexical·multi_doc + 고난도), 14B 생성 노이즈, TEI 임베딩·리랭커 운영 설정, 2026-10-24.
원자료·회귀 덤프(실문서 조각 포함)는 `eval/results/scale_noise/`(gitignore).

## 결론

1. **규모는 절벽이 아니라 완만한 내리막이다.** 테넌트 조각 444 → 13,768(×30)에서 Hit@1 0.830 → 0.809(−2.1pp), R@5 0.979 → 0.950(−2.9pp),
   R@20 1.0 → 0.965. 세미나의 "수백·수천 문서면 급격히 떨어진다"는 지적은 이 코퍼스·이 구성(필터 안 kNN + 어휘 주입 + 리랭커)에선 재현되지 않는다.
2. **내리막의 원인은 둘이고 둘 다 자리를 찾았다.**
   - 같은 도메인 노이즈의 밀어내기(정확 탐색도 정답을 30위 밖으로 놓침: 4 → 7문항). 조 번호 질문("제N조 내용")에 집중 — 규정이 많아지면
     같은 조 번호가 여러 문서에 있어 식별자 채널(#238)이 문서를 못 가른다. 사람도 문서를 지정해야 답할 질문이다.
   - **HNSW 근사 누락**: 정확 탐색엔 30위 안(대부분 1위)인 정답을 근사 탐색이 놓친 문항이 0(×5) → 3(×10) → 9(×30). 근사 탐색은
     현 규모(x0 29.7/30)에서도 돌고 있고, 규모가 커지며 놓치는 수가 는 것이다. 다만 9건 중 7건은 어휘 채널 주입+리랭커가 Hit@1 1.0으로
     구제해 **최종 지표의 내리막은 대부분 위의 밀어내기다**(`ef_search` 400으로 누락을 0으로 만들어도 최종 수치가 안 움직인다, 아래). 남는 건
     어휘 겹침이 없는 질문 2건(R@20 밖).
3. **IDF 공유 영향 없음.** 같은 노이즈 13,324조각을 다른 테넌트로 넣은 인덱스(idf)에서 inticube 수치는 x0와 같다(Hit@1 0.837 vs 0.830 — 잡음 범위).
   9/13의 0.829→0.817은 삭제 대기 문서(같은 테넌트)였지 IDF가 아니었다.
4. **`rag/os_client.py`의 "15,000 미만이면 정확 탐색" 주석은 우리 엔진(lucene)에 해당이 없다.** `approximate_threshold`는 k-NN 플러그인
   2.18 소스에서 네이티브 엔진 writer(`NativeEngines990KnnVectorsWriter`)만 쓰고, lucene은 `Lucene99HnswVectorsFormat`으로 항상 그래프를
   만든다. 실측도 x0(444조각)에서 이미 근사∩정확 29.7/30이다. lucene이 정확 탐색으로 빠지는 조건은 따로 있다 — 필터 통과 문서 수가
   탐색 후보 수 이하일 때(idf 조건: 전체 15,284 중 inticube 444 → 30/30). → 주석을 실측과 재검토 트리거로 고쳤다(이 PR).

## 회귀 문항 13건(x0 대비, 조건 누적)의 유형

| 유형 | 건 | 모양 |
|---|---|---|
| 조 번호 질문 | 2문항 × 3조건 | "제N조 내용" — 노이즈 규정 여러 편의 같은 조 번호가 상위 5를 채움. ×5부터 Hit@1 0, ×10부터 R@5 0 |
| 같은 주제의 노이즈 | 4문항 | 겸직·괴롭힘·소프트웨어 신청처럼 노이즈 규정이 질문 주제와 겹침. 정답은 2~3위로 밀림(R@5 유지) |
| HNSW 누락 | 9문항(×30) | 정확 탐색 1위인 정답이 근사 30에 없음 → 어휘 채널로 7건 복귀, 2건 R@20 밖 |
| 실문서 내부 순위 | 1문항 | 같은 조의 하위 조(43조의 2·3·4)가 정답 문단을 밀어냄 — 노이즈와 무관한 라벨 세부 문제 |

"같은 주제의 노이즈"는 주제 선정이 골드와 비켜섰는데도 생겼다 — 규정집이 많아지면 피할 수 없는 모양이고, 정답이 상위 5 안에 남아
생성이 받는다. 이슈가 걱정한 "엉뚱한 청크"는 전부 **그럴듯한 이웃**이지 무관한 조각이 아니었다.

## ef_search 보조 실험(x30 임시 인덱스, 질의 파라미터 `method_parameters.ef_search`)

놓친 9문항만: 기본(100) 0/9 복귀, 200 → 7/9, 400 → 9/9, 1000 → 9/9. 지연 42 → 46ms(차이 없음).
전체 141문항 풀 재측정(x30, ef_search 400): 근사∩정확 26.0 → **29.9/30**, 상위1 일치 0.929 → **1.000**, 정답∈근사30 0.887 → **0.950**(= 정확 탐색),
근사 지연 36ms(동일). 즉 13.8k 조각에서의 근사 누락은 ef_search 400으로 완전히 사라진다.

그런데 **최종 지표는 안 움직인다** — 놓친 9문항 중 7건은 기본 설정에서도 이미 Hit@1 1.0이었다. 어휘 채널 주입(BM25 상위 15)이 그 조각을
풀에 다시 넣고 리랭커가 1위로 올렸기 때문이다. ef_search 400으로 전체를 다시 돌린 최종 수치(x0 0.837/0.979, x30 0.794/0.950)의 차이는
회차 간 흔들림(문항 2건, 양방향)이다. 결론: 현 하이브리드 구성이 근사 누락을 가리고 있고, ef_search는 "어휘 겹침이 없는 질문"을 위한
안전판이다 — 운영 반영 여부는 아래 "결정" 참조.

## 노이즈 코퍼스

- 생성 2,000편(14B, 온도 0.8, 동시 20, 약 110분·합산 약 660 tok/s). 회사 규정 꼴 1,000(측정 테넌트에 없는 규정 50종 × 가상 회사 20)
  + 다른 도메인 1,000(쇼핑몰·여행·약관 50종 × 가상 브랜드 20). 편당 평균 2,200토큰·약 12조각(SentenceSplitter 512).
- 골드 겹침 필터로 696편 제외(35%): 잘림 6, 사실 겹침 690 — 측정 테넌트 골드 3문항의 흔한 기간 값(3·6개월, 1·3개월, 5·10년)이 대부분.
  보수적인 방향이라 그대로 뒀다(남은 1,304편 > 필요 1,139편). 대가: 기간 값이 흔한 주제(사택·기숙사, 기록물 보존)가 거의 빠졌다.
- 표본 12편 육안: 장·조 구조, 가상 회사명, 주제 다양성 의도대로.
