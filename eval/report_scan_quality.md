# 스캔 PDF 품질 분석 (#224)

측정일 2026-10-19 · 기준 main f087bc6 · OCR = worker15 Triton RapidOCR(PP-OCRv5 mobile, korean) · 도구 `eval/scan_quality`

## 요약

- **스캔 PDF 제목 깨짐의 원인은 OCR 서버의 글자 검출 크기 설정이다.** RapidOCR 기본값 `Det.limit_type=min · limit_side_len=736`은
  넘겨받은 이미지의 짧은 변을 736px로 **키운다**. docling은 쪽을 통째로 OCR하지 않고 레이아웃 영역을 잘라 보내므로, 납작한
  제목 띠(834×118px)가 6배 넘게 불어나 검출이 흔들렸다.
- **`Det.limit_type=max`(키우지 않음)로 고친다.** 합성 스캔 5건 제목 깨짐 2 → 0, 표 이미지 하네스는 약간 이득, 실문서는 거의 불변,
  문서 단위 검색은 동일. 서버 재기동 후 GPU 확인이 남는다.
- 본문 **띄어쓰기 소실은 OCR 모델의 한계로 남는다**(#253과 같은 결론). 유지율 0.6~0.8. 문서 단위 검색 손해는 측정되지 않았다.
- 실제 스캔본이 없어 **합성 스캔**(디지털 PDF를 렌더 후 열화)으로 쟀다. 결론은 합성 조건 기준이다.

## 재현과 원인

같은 쪽 이미지(150dpi 합성 스캔)의 제목 영역을 여백만 바꿔 OCR 서버에 보낸 결과:

| 보낸 이미지 | 현행(min 736) | max |
|---|---|---|
| 쪽 전체(짧은 변 1,836px — 키우지 않음) | 기부금영수증 발급 규정(GP-CS-003) | 같음 |
| 제목 띠, 여백 0px | (GP-CS-003) / 박급 / 규정 / 발급 | 기부금영수증 발급 규정(GP-CS-003) |
| 여백 9px | 기부금영수증 발급 규정(GP-CS-003) | 같음 |
| 여백 30px | 금영 / 밤 / (GP-CS-003) / T / 0 | 기부금영수증 발급 규정(GP-CS-003) |
| 여백 90px | 기부금영수증 / 발급 / 규정 / … + 아랫줄 잔해 | 기부금영수증 발급 규정(GP-CS-003) |

색인된 청크에서는 이 깨진 제목("D 금영 0 밤 D 정 G -003)")이 문서 **모든 청크의 heading_path 맨 앞**에 붙었다.

기각한 레버:
- **OCR 배율**(현행 3.0): 원인이 아니다. 쪽 전체 OCR에서는 배율 1~4 모두 제목을 바르게 읽었다.
- **쪽 전체 OCR 모드**(`OcrMode.FULL_PAGE`): 제목은 고치지만 본문이 나빠진다. 100dpi 문서에서 띄어쓰기 유지 0.64→0.16, 글자 일치 0.993→0.782.
- 큰 이미지 축소는 설정과 무관하다. 검출 앞의 `Global.max_side_len=2000`이 이미 줄인다. 그래서 `max`의 실제 차이는 "작은 영역을 키우지 않음" 하나다.

## 측정

로컬 CPU에서 서버와 **같은 엔진·같은 파라미터**로 돌렸다(`ocr_variant`). 서버 대표성은 먼저 확인했다.
- 표 하네스: 셀 단위 완전 일치.
- 본문: 글머리표 줄 순서만 다르다(#168의 GPU·CPU 줄 묶음 차이와 같은 종류).
- 서버는 두 번 돌려도 바이트 단위로 같았다.

### 1. 합성 스캔 5건 (`compare`, 정답 = 같은 원본 디지털 PDF의 청킹)

| 문서(열화 조건) | 제목 | 헤딩 일치 | 문장(공백 무시) | 띄어쓰기 유지 |
|---|---|---|---|---|
| goodpeople_03 (150dpi) | ✗ → ✓ | 0.92 → 1.00 | 0.74 → 0.84 | 0.68 → 0.71 |
| homeplus_05 (200dpi + 1.5° 기울기) | ✓ → ✓ | 1.00 → 1.00 | 0.86 → 0.90 | 0.80 → 0.79 |
| harim_13 (300dpi + 잡음·번짐) | ✓ → ✓ | 0.00 → 0.00 | 0.19 → 0.19 | 0.67 → 0.66 |
| adererror_03 (100dpi) | ✗ → ✓ | 0.75 → 1.00 | 0.65 → 0.65 | 0.64 → 0.59 |
| aromanica_03 (200dpi + 조명 얼룩 + JPEG 35) | ✓ → ✓ | 0.92 → 1.00 | 0.85 → 0.88 | 0.72 → 0.70 |

- 값은 현행 → max.
- harim_13은 두 설정 모두 표 구조가 무너진다(표 머리 행이 헤딩으로 잡힘). 이 설정과 무관한 별개 결함이다.
- 글자 그대로(공백 포함) 일치하는 문장은 0.0~0.4다. 띄어쓰기 소실 때문이다.
- 글자 일치(difflib)는 줄 순서에 민감해 문서 간 비교에 쓰지 않았다.

### 2. 표 이미지 하네스 (#246/#253 23축, 533칸)

| | 이미지 표 셀 | 숫자 칸 | 텍스트 PDF 표 |
|---|---|---|---|
| 현행 | 430 | 294 / 338 | 불변 |
| max | 431 | 297 / 338 | 불변 |

- 바뀐 표는 4개다.
- 잃은 2칸은 띄어쓰기 하나씩이다("부산 창고" → "부산창고").
- 얻은 칸에는 현행에서 빠지던 한 자리 숫자 칸 3개가 들어 있다.

### 3. 실문서 (이미지가 있는 PDF 4건, 현행 → max 청크 비교)

|---|---|
| 2건 | 0 |

### 4. 문서 단위 검색 (대상 5건의 골드 63문항, 정답 문서가 처음 나오는 순위)

| 판 | top-1 (homeplus · adererror · aromanica · goodpeople · harim) | top-5 (같은 순서) | 20위 밖 |
|---|---|---|---|
| 디지털 | 0.75 / 0.62 / 0.71 / 0.73 / 0.70 | 1.00 / 0.88 / 1.00 / 0.82 / 1.00 | 0 |
| 스캔(현행) | 0.80 / 0.50 / 0.71 / 0.73 / 0.80 | 같음 | 0 |
| 스캔(max) | 0.80 / 0.50 / 0.71 / 0.73 / 0.80 | 같음 | 0 |

- 제목 깨짐과 띄어쓰기 소실은 **문서 단위 검색에는 거의 손해가 없다**. 같은 문서의 다른 청크와 파일명이 받쳐 준다.
- 손해는 표시에 남는다. 출처 경로와 청크 머리말에 깨진 제목이 보인다.
- 스니펫 단위(정답 청크)는 띄어쓰기가 달라 골드로 풀 수 없어 재지 않았다.

## 남은 것

- 서버 재기동 후 GPU 확인: CUDA EP 정상 여부와 표 하네스 결과가 로컬과 같은지.
- 스캔본 감지·안내: 스캔본은 지금도 "이미지가 쪽 면적의 N%" 경고(`status_reason`)를 받는다. 추가 안내는 실스캔 수요가 생기면 판단한다.
- 잡음 많은 스캔의 표 구조 붕괴(harim_13): 별도 이슈.
- 실제 스캔본이 들어오면 같은 도구로 다시 잰다. `scans.py`의 SPECS에 원본 디지털판을 두고 스캔판을 넣으면 된다.

## 재현

```bash
python -m eval.scan_quality.scans                                    # 합성 스캔 5건
python -m eval.scan_quality.compare remote local_min736 local_max    # 문서 대조 → eval/results/scan224/compare.html
python -m eval.scan_quality.retrieval swap remote && python -m eval.scan_quality.retrieval measure remote
python -m eval.scan_quality.retrieval swap digital                   # 개발계 원복
```
